# 汉江（HanJiang）二期方向规划（建议稿）

> 定位：在一期「功能完备、可部署运行」基础上，围绕**开放平台对外化、消息与内容体系增强、AI 助手工具化、多租户与数据权限**四大主题展开，将平台从「内部管理后台」升级为「可对外服务、可多租户运营」的企业级基座。
>
> 本文档为规划建议稿：每个方向均给出现状基线、二期目标、功能拆解、涉及模块与验收要点，供评审与排期参考。

---

## 一、二期总体目标

| 维度 | 一期现状（基线） | 二期目标 |
|---|---|---|
| 开放能力 | 开放平台 API（`/api/open/v1` 9 端点）与 HMAC 签名协议已可用，但**无对外门户**（`web/open` 仅 README 占位） | 门户落地：注册、控制台、文档中心、调试沙箱、用量统计，形成「申请 → 授权 → 联调 → 运营」闭环 |
| 消息体系 | 通知多渠道（站内信/邮件/钉钉/飞书/短信）+ 失败重试；公告单后台形态 | 通知模板引擎 + 定时推送 + 推送效果统计；公告多端展示（App/门户/邮件摘要） |
| AI 能力 | SSE 流式对话、会话管理、记忆压缩、知识库检索、工具编排（`openai_compat`） | 工具集扩展：开放平台 API 编排、受控数据查询，工具注册框架化 |
| 权限与租户 | RBAC（角色-权限-菜单）+ 权限自动注册 + 实时鉴权 | 多租户隔离 + 行级/字段级数据权限 |

**二期原则**：不推翻一期分层架构（API → Services → Repositories → Models/Infras），全部新能力以增量模块方式落入既有骨架；数据面新增表一律走 Alembic 迁移。

**范围边界**：文件能力增强（在线预览 / 回收站）明确**不在**二期范围内，二期不对 `files` 相关能力做增量投入。

---

## 二、方向 1：开放平台门户（web/open）对外落地

### 现状基线
- 后端已有：`src/api/open/v1`（app / health / user），AppId/AppKey 生命周期、密钥轮换、scope 授权、`plain` / `hmac` 双鉴权，时间窗 300s 防重放；
- 前端 `web/open` **仅有 README.md**，门户为空白。

### 二期功能拆解

| 模块 | 功能点 | 说明 |
|---|---|---|
| 门户基础 | 独立前端工程（Vue 3 + TS，沿用 #409eff 品牌色），域名/路由与 admin 分离 | 面向第三方对接方，非内部用户 |
| 注册与认证 | 开放平台账号注册/登录、主体信息（企业名称、联系人）、邮箱验证 | 与用户体系解耦，或复用 users 表加 `is_open_developer` 标记（二选一，评审时定） |
| 应用控制台 | 应用创建、AppId/AppKey 查看与轮换、scope 申请与授权状态、回调地址管理 | 复用 `openapi_apps` / `openapi_scopes` 表 |
| 文档中心 | API 文档（Swagger 聚合 + 对接指南）、签名计算示例（Python/Go）、常见错误码表 | 一期《开放平台对接指南》迁移为门户在线文档 |
| 调试沙箱 | 在线构造请求、自动生成签名、请求回显与响应解析 | 显著降低第三方接入门槛 |
| 用量与审计 | 调用量统计（按应用/接口/时间）、异常率、操作审计 | 新增 `openapi_call_logs` 表（见数据面） |
| 应用审批流 | 应用创建/scope 变更走管理员审批（复用通知体系推送审批结果） | 避免开放 API 无管控开放 |

### 涉及模块 / 验收要点
- 后端：`src/api/open/v1` 扩展（统计、审批）、`src/services` 新增 `openapi_portal_service`；
- 验收：第三方按文档 30 分钟内完成签名对接并成功调用 `/users` 系列接口；管理员可审批与回收应用权限。

## 三、方向 2：通知模板引擎与定时推送

### 现状基线
- 通知已有：普通/维护两类、站内信广播 + 多渠道抽象（station/email/钉钉/飞书/短信）、用户偏好、Redis 队列失败重试（RetryWorker，60s 轮询，max_retries=3）。

### 二期功能拆解

| 模块 | 功能点 | 说明 |
|---|---|---|
| 模板引擎 | 事件类型 → 模板绑定（Jinja2），支持变量渲染（如 `{{ user.name }}`）、多渠道各自正文/标题模板 | 新增 `notification_templates` 表；邮件/钉钉等渠道从「写死正文」改为「模板渲染」 |
| 定时推送 | 计划任务：指定时间/周期推送（cron 语义），支持维护通知的预定时发布 | 复用 `src/scheduling`（现有 retry_worker 同架构，新增 `scheduler_worker`），不引第三方任务框架 |
| 推送效果 | 送达率、已读率、渠道失败分布统计；站内信已读回执已具备，补聚合统计接口 | 新增 `notification_delivery_stats`（可定时任务聚合） |
| 触达增强 | 批量推送分批限速、按用户偏好过滤目标人群、未读用户二次提醒 | 与 user_notification_preferences 联动 |

### 涉及模块 / 验收要点
- 后端：`src/notification` 扩展、`src/scheduling` 新增 worker、`src/api/v1/notification.py` 扩展；
- 验收：维护通知可预约定时发布；邮件内容由模板变量渲染；推送失败仍走 Redis 重试链路。

## 四、方向 3：公告多端展示（App / 门户 / 邮件摘要）

### 现状基线
- 公告已有：CRUD、Markdown/富文本、有效期（过期自动下架）、首页 Banner + 板块展示、发布/编辑/上架/下架/删除全量审计。

### 二期功能拆解

| 模块 | 功能点 | 说明 |
|---|---|---|
| 多端接口 | 公告按「端」过滤查询（admin / open 门户 / App），仅返回该端启用的公告 | 一期单后台展示，二期增加展示端维度（公告表加 `target_platforms` 字段或独立关联表） |
| App 展示 | H5/小程序公告中心：列表 + 详情 + 已读状态 | 复用 `announcements` 表，前端新增轻量页面 |
| 门户展示 | 开放平台门户首页公告位（产品动态、维护通知） | 与方向 1 门户联动 |
| 邮件摘要 | 定期聚合公告/维护通知为摘要邮件（如每周一 09:00） | 复用通知渠道 email + 定时推送（与方向 2 协同） |
| 运营增强 | 公告置顶、阅读统计（曝光/已读） | 新增 `announcement_reads` 表 |

### 涉及模块 / 验收要点
- 后端：`src/api/v1/announcement.py` 扩展端维度与阅读统计；
- 验收：一条公告可指定展示端并仅在对应端可见；邮件摘要按周期到达且内容聚合正确。

## 五、方向 4：AI 助手工具集扩展（开放平台 API 编排、数据查询）

### 现状基线
- AI 已有：SSE 流式对话（token/navigate/done）、会话管理、记忆压缩、知识库检索、工具编排、`openai_compat` 协议（可对接 DeepSeek/火山方舟/通义/vLLM）、对话反馈。

### 二期功能拆解

| 模块 | 功能点 | 说明 |
|---|---|---|
| 工具注册框架 | 将现有工具编排升级为「工具注册表」（名称、schema、执行器、权限声明），启动自动注册 | 对齐一期权限自动注册的工程风格（`@tool` 装饰器 + 启动扫描） |
| 开放平台 API 编排 | 将 `/api/open/v1` 能力注册为可调用工具，助手代第三方完成应用管理/数据查询 | 工具调用走 openapi 鉴权链路，调用行为入审计 |
| 受控数据查询 | 自然语言 → SQL 查询工具：仅允许只读 SELECT、强制行级权限过滤、查询超时与结果截断、敏感列脱敏 | **安全边界是核心验收项**：任何情况下不可绕过 RBAC 与数据权限 |
| 多模型路由 | 按场景路由模型（轻量问答/深度推理），对话与工具调用分离计费/限额 | 对接现有 `openai_compat` 配置体系 |
| 助手运营 | 工具调用日志、成功率、token 消耗统计 | 复用 `assistant_messages`，扩展 `tool_calls` 记录 |

### 涉及模块 / 验收要点
- 后端：`src/assistant` 扩展工具注册与执行器，`src/infras` 加数据查询网关；
- 验收：助手可通过工具完成开放平台应用查询；SQL 工具在越权/危险语句下被拒绝且入审计。

## 六、方向 5：多租户支持与更细粒度数据权限

### 现状基线
- 已有 RBAC：角色-权限-菜单、权限自动注册、超管 `*` 通配、实时鉴权；单租户模型（所有用户共享同一数据空间）。

### 二期功能拆解

| 模块 | 功能点 | 说明 |
|---|---|---|
| 租户模型 | 新增 `tenants` 表；租户隔离策略选型：**共享库 + `tenant_id` 行级隔离**（成本低、运维简单，推荐） | 优先行级方案，避免独立库/独立 schema 的运维成本；评审时确认 |
| 数据权限 | 数据范围维度：全部 / 本部门 / 本人（用户表、审计日志、文件等按范围过滤） | 新增 `data_scope` 概念，与 RBAC 组合为「角色决定能否，范围决定看多少」 |
| 字段权限 | 敏感字段（如邮箱、手机号）按角色可见性控制 | 序列化层统一处理，避免散落各接口 |
| 改造范围 | 核心表（users、files、audit_logs、announcements）先加 `tenant_id` + Alembic 迁移 + 存量数据默认租户 | 全链路 `require_tenant` 依赖注入，与现有鉴权依赖同构 |
| 运营工具 | 租户管理（创建/启停/配额）、租户内管理员委派 | 复用 RBAC，新增超管专属视图 |

### 涉及模块 / 验收要点
- 后端：`src/api/dependencies.py` 加租户依赖、`src/models` 加租户字段、`src/repositories` 加范围过滤基类；
- 验收：跨租户数据访问被拦截；同一角色在不同数据范围内查询结果不同；迁移对存量数据无损。

## 九、优先级与里程碑建议

| 优先级 | 方向 | 理由 |
|---|---|---|
| P0 | 开放平台门户（方向 1） | 对外价值最高、`web/open` 已占位、后端 API 已就绪，边际成本最低 |
| P1 | 通知模板与定时推送（方向 2） | 依赖通知现有链路，模板化是后续多端公告的前提 |
| P1 | 公告多端展示（方向 3） | 部分依赖方向 2 的定时/模板能力，可紧随其后 |
| P1 | AI 助手工具集（方向 4） | 价值高，但需先明确工具注册框架与数据查询安全边界 |
| P2 | 多租户与数据权限（方向 5） | 工程改动面最大（核心表迁移），建议放在二期后段或独立三期，避免与 P0/P1 并行引入回归风险 |

**里程碑划分建议**：M1 = 方向 1（对外闭环）；M2 = 方向 2 + 方向 3（消息内容体系）；M3 = 方向 4 + 方向 5（智能化与租户化）。

## 十、二期风险与依赖

| 风险 / 依赖 | 说明 | 缓解措施 |
|---|---|---|
| SQL 工具安全 | 自然语言转 SQL 天然有越权/注入风险 | 只读白名单 + 行级过滤强制注入 + 超时/截断 + 全量审计，灰度开放 |
| 多租户改造回归 | 核心表加 `tenant_id` 影响全部查询链路 | 独立里程碑、分批迁移、存量数据默认租户、回归测试先行 |
| 门户与用户体系 | 开放开发者账号与内部 users 表关系需评审定案 | 优先解耦（独立 open 账号），避免污染内部 RBAC |
| 定时任务可靠性 | 新增 scheduler_worker 与现有 RetryWorker 并存 | 沿用同架构、复用 Redis 队列与日志规范 |
